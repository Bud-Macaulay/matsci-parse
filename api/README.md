# matsci-api

HTTP layer that auto-exposes the top-level function exports of `matsci-parse`
as `POST /api/<functionName>` endpoints. It lives in its own pnpm workspace
package (like `webapp/`); the library itself is untouched.

## How it works

- The server imports the **built** library (`matsci-parse` → `dist/index.js`,
  produced by the existing root `pnpm build`) **exactly once** at startup.
  Every request reuses those same function references, so the Node process
  stays persistent, V8 keeps JIT-optimized code hot, and in-memory state
  (module caches, initialized wasm) is preserved across calls.
- At startup every export is inspected: only plain functions become routes.
  Data objects (`PeriodicTable`, `EPSILON`, …), namespaces (`kpoints`) and
  class constructors are skipped and reported in the startup log.
- Sync functions return directly; async functions are awaited.

## Run

From the repo root:

```sh
pnpm build                  # build the library once (provides dist/index.js)
pnpm --filter matsci-api start
pnpm --filter matsci-api dev   # watch mode

# Structure + IO only, grouped subpaths, no flat root routes:
pnpm --filter matsci-api start:structure-io
# (equivalent to API_GROUPS=structure,io API_FLAT_ROUTES=false ... start)
```

## Endpoints

| Method | Path            | Description                                            |
| ------ | --------------- | ------------------------------------------------------ |
| GET    | `/healthz`      | `{status, functions}`                                  |
| GET    | `/api`          | `{functions: [...]}` sorted list of exposed names      |
| GET    | `/openapi.json` | Autogenerated OpenAPI 3.1 spec for the exposed routes  |
| GET    | `/docs`         | Human-readable function listing                        |
| POST   | `/api/<name>`   | Call a function: body `{"args": [...]}` → `{"result"}` (absent when `API_FLAT_ROUTES=false`) |
| POST   | `/api/<group>/<name>` | Same call via the group subpath, e.g. `/api/io/fromPOSCAR` |
| POST   | `/api/batch`    | Many calls, one round trip (see below)                 |

Example:

```http
POST /api/gcd
Content-Type: application/json

{"args": [48, 18]}
```

```json
{ "result": 6 }
```

TypeScript objects are returned as plain JSON. `undefined` results become
`null`. Results that cannot be serialized (e.g. `bigint`) fail with a
`SERIALIZATION_ERROR` instead of crashing the request.

### Groups

Functions are grouped by the `lib/core/*` barrel they resolve through
(`structure`, `io`, `site`, `lattice`, `math`, … — see `GET /api`, which
returns a `groups` map). Two things follow:

- `API_GROUPS="structure,io"` exposes only those barrels — the simplest way
  to serve just structure + IO and nothing else. Unknown group names match
  nothing. Combines with `API_ALLOWLIST`/`API_DENYLIST`.
- Every function is also reachable under its group subpath:
  `POST /api/io/fromPOSCAR` ≡ `POST /api/fromPOSCAR`. A wrong group
  (`/api/structure/fromPOSCAR`) is a 404.
- `API_FLAT_ROUTES=false` drops the flat `POST /api/<name>` routes
  entirely, leaving grouped subpaths only (plus `/api/batch`, `/api`,
  `/healthz`, docs). Unmatched `/api/*` paths return JSON `NOT_FOUND`,
  never Express's HTML page.

### IO and strings

IO readers take plain strings and return structures; writers take structures
and return strings. Structures are ordinary JSON-able objects, so workflows
chain client-side with the server holding no session state:

```sh
# 1. parse
curl -X POST localhost:3000/api/io/fromPOSCAR \
  -H 'Content-Type: application/json' -d @poscar.json
# {"result": {"lattice": {...}, "sites": [...], ...}}
# 2. analyse / convert, passing the structure back in {"args": [<structure>]}
```

(`poscar.json` is `{"args": ["<POSCAR text>"]}` — build it with e.g.
`python -c "import json;print(json.dumps({'args':[open('POSCAR').read()]}))"`.)
Watch `API_BODY_LIMIT` for large files. `api/examples/call_api.py` shows the
full parse → formula → CIF round trip.

### Batching

`POST /api/batch` accepts `{"calls": [{"fn": "<name>", "args": [...]}]}`
and runs the calls sequentially in order, returning per-item outcomes so one
failure does not sink the batch:

```json
{ "results": [{ "ok": true, "result": 6 }, { "ok": false, "error": {...} }] }
```

Batch size is capped (`API_MAX_BATCH`, default 50). This is the only
batching provided — per the brief, no further optimization up front.

## Docs

`GET /openapi.json` serves an OpenAPI 3.1 document generated at startup from
the actually-exposed functions, so it cannot drift from the routes (covered
by tests). `GET /docs` renders it with Swagger UI (assets served locally via
`swagger-ui-express`, so it works offline, with try-it-out).

Operation summaries, argument lists and return docs come from the library's
own TSDoc comments, extracted at build time into `src/fn-docs.ts` (generated
file, checked in). The extractor resolves the true top-level export closure
of `lib/main.ts` (`export *`, named re-exports, aliases), so internal helpers
are never included and each doc comes from the declaration that actually wins
the export. Refresh after library changes with:

```sh
pnpm --filter matsci-api docs:extract
```

No off-the-shelf extractor was usable here: the repo is on TypeScript 7
(native), whose programmatic API no longer exposes the classic `ts.*`
surface, so `typedoc` (a repo devDependency) currently crashes on this
codebase — the extractor is therefore a small purpose-built line parser, see
`scripts/extract-fn-docs.ts`.

### Standards conformance

The wire format is intentionally plain RPC JSON (`{"result": ...}` /
`{"error": {"code", "message"}}`), **not** [JSON:API](https://jsonapi.org/):
JSON:API mandates `data`/`errors` top-level resource documents, which fits
REST resources but adds ceremony with no payoff for function-call RPC, and
would contradict the `{"result": 60}` contract above. Interop with generic
tooling is provided via the OpenAPI spec instead.

## Errors

All errors are JSON: `{"error": {"code": "...", "message": "..."}}`.

| Status | Code                 | Meaning                              |
| ------ | -------------------- | ------------------------------------ |
| 400    | `INVALID_JSON`       | Body is not valid JSON               |
| 400    | `INVALID_ARGS`       | Body must be `{"args": [...]}`       |
| 404    | `UNKNOWN_FUNCTION`   | No such exposed function             |
| 405    | `METHOD_NOT_ALLOWED` | Function routes accept POST only     |
| 413    | `PAYLOAD_TOO_LARGE`  | Body exceeds `API_BODY_LIMIT`        |
| 500    | `FUNCTION_ERROR`     | The library function threw           |
| 500    | `SERIALIZATION_ERROR`| Result is not JSON-serializable      |

## Configuration (env)

| Variable        | Default | Description                              |
| --------------- | ------- | ---------------------------------------- |
| `PORT`          | `3000`  | Listen port                              |
| `API_BODY_LIMIT`| `1mb`   | Max JSON body (passed to `express.json`) |
| `API_ALLOWLIST` | —       | `API_ALLOWLIST="gcd,parseFormula"`: expose only these |
| `API_DENYLIST`  | —       | Never expose these, even if allowlisted  |
| `API_GROUPS`    | —       | `API_GROUPS="structure,io"`: expose only these barrels |
| `API_FLAT_ROUTES` | `true` | `false`: grouped subpaths only, no flat `/api/<name>` routes |
| `API_MAX_BATCH` | `50`    | Max calls per batch request              |

## Python

`examples/call_api.py` uses only the standard library (`urllib`):

```sh
python api/examples/call_api.py
BASE_URL=http://example:3000 python api/examples/call_api.py
```

## Tests

Tests live in `api/tests/` and run with the repo's vitest setup from the
repo root (`pnpm test:run`). They inject the library source directly, so no
build is needed to test. Typecheck the workspace with
`pnpm --filter matsci-api typecheck`.
